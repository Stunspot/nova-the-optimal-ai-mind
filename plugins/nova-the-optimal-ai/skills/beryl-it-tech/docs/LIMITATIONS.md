# Limitations and claim boundaries

Beryl IT Benchcraft provides occupational reasoning, planning, explanation, case continuity, and review. Its answer is only as current and grounded as the supplied device state, sources, tools, and accountable authority.

## No automatic contact with the machine

Beryl cannot see, hear, smell, meter, open, power-cycle, repair, image, back up, or verify a device unless the host exposes a real capability or an authorized person supplies evidence. Text that describes an action does not prove that it happened.

## No implied access or authority

The package supplies no credentials, remote-management access, vendor portal, licensed service data, warranty authority, organizational permission, purchasing authority, incident-response custody, or right to access another person’s files.

Permission to inspect does not imply permission to change configuration, install software, reset credentials, replace parts, spend money, wipe data, dispose of media, or declare completion.

## Version-sensitive facts can expire

Firmware, drivers, model compatibility, commands, service status, security advisories, warranty terms, support policy, and vendor procedures can change. Consequential instructions require the actual device and version plus current primary-vendor authority. Durable diagnostic method does not make remembered specifics current.

## Platform depth is uneven

The release contains deep embedded Windows and network knowledge. macOS and Linux are supported through the same physical-to-application diagnostic method and platform-native source routing, but their embedded technical depth is lower. Current platform documentation may be required earlier.

## Safety and specialist custody remain human

The package does not replace a qualified repair technician, electrician, battery specialist, data-recovery laboratory, security incident responder, managed-service administrator, or accountable system owner.

High-energy hardware, swollen batteries, liquid damage, unstable storage containing unique data, destructive recovery, board repair, managed-device compromise, credential bypass, and irreversible changes require the appropriate human custodian.

## Diagnosis and repair remain distinct

A plausible explanation is not a confirmed cause. A changed setting, replaced part, successful boot, completed command, or quiet interval is not proof of repair. Verification must recreate the original triggering conditions closely enough to decide the claim and check functions disturbed by the work.

## Case validation is structural

`scripts/validate_case_file.py` checks required fields, controlled states, array types, verification disposition, and a populated next action. It does not establish that evidence is accurate, a command ran, a change was authorized, or a case is safe to close.

## Behavioral evaluation is bounded

The included evaluation suite tests selected behaviors in isolated text episodes. Results apply only to the recorded package, model, host, adapter, context, and trial. They do not establish universal reliability, physical repair success, current vendor applicability, accessibility conformance, commercial approval, or target-host installation.

## Release-specific verification boundary

The v0.1.0 build passed structural package, resource, schema, example-case, ZIP round-trip, and evidence-integrity checks. Local behavioral runs were useful but showed stochastic completeness variance and one documented weak judge oracle. The independent review disposition was `REVIEW_PASS_WITH_CONDITIONS`, not an unqualified reliability certification.

Installation, fresh-task discovery in a target host, physical device work, live vendor lookup, credential use, and cross-model reliability were not performed during the build.
