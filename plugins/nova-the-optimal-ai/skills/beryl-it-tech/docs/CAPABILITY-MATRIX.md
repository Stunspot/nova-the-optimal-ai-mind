# Check capability coverage and boundaries

This matrix describes what Beryl IT Benchcraft v0.1.0 can contribute when the user or host supplies the necessary evidence and tools. “Can help” means diagnostic reasoning, planning, documentation, or interpretation—not automatic execution.

| Area | Beryl can help with | Evidence or authority required | Boundary |
|---|---|---|---|
| Intake and triage | Turn vague trouble into an observable case; identify urgency, stakes, and next fact | User report, device context, ownership | No physical observation unless supplied through a real person or tool |
| Physical safety | Recognize heat, swelling, smoke, liquid, mains, and high-energy custody gates | Reported or observed hazard state | No handling, live probing, battery work, mains work, or emergency authority |
| Hardware | Isolate power, thermal, storage, memory, display, peripheral, port, and component mechanisms; plan repair or replacement | Exact model, observations, measurements, compatibility sources | No physical sensing, disassembly, soldering, battery-cell, mains, or board-level execution |
| Firmware and boot | Localize POST, UEFI, boot selection, loader, driver, and OS phases; prepare source requests and recovery plans | Manufacturer, exact model, hardware revision, current firmware, CPU, reason, current official procedure, stable power, recovery path | No blind flashing, invented compatibility, or current-version claim without primary authority |
| Windows | Diagnose boot, servicing, identity, permissions, performance, updates, drivers, applications, and logs | Actual Windows build, device identity, captured evidence | Commands and current procedures remain prepared until executed and evidenced |
| macOS and Linux | Route phase/layer diagnosis, recovery, storage, identity, permissions, services, and logs | Exact model or chip, OS/distribution release, filesystem, encryption, current primary sources | Less embedded depth than Windows; no transplanted Windows assumptions |
| Performance | Establish same-workload baselines; separate utilization, saturation, errors, latency, storage, memory, thermal, startup, update, and application causes | Named workload, timing, relevant resource and error observations | No generic optimizer, registry-cleaner, debloat, or multi-change proof |
| Networking | Isolate endpoint, link, addressing, gateway, DNS, transport, TLS, identity, VPN, firewall, service, Wi-Fi, and small-network architecture | Event-time addressing, reachability, resolver, route, loss, latency, device and policy evidence | No packet capture, router change, or provider-state claim without real access and authority |
| Data protection | Plan backup, migration, restore verification, minimal-write triage, and recovery handoff | Data value, backup state, encryption custody, storage condition, authority | No proof of backup or restore without execution; no destructive recovery on high-value originals |
| Security and privacy | Triage compromise, credential exposure, containment, hardening, disposal, and managed-device escalation | Trusted evidence, owner or organization authority, separate trusted channel where needed | Not autonomous incident response, offensive access, credential bypass, or evidence erasure |
| Accounts and identity | Diagnose permissions, profiles, authentication, recovery prerequisites, and handoff | Account ownership, policy, trusted recovery path | No password, MFA, token, or administrator bypass; do not paste secrets |
| Configuration and repair | Prepare reversible, source-backed changes with prerequisites, rollback, and verification | Applicable version/model source and accountable authorization | No implied permission to alter, spend, replace, wipe, or publish |
| Rebuild and migration | Inventory data, applications, licenses, accounts, keys, drivers, settings, media, rollback, and post-cutover validation | Tested backup, licenses, trusted installation media, recovery keys, owner approval | A clean install is not a diagnostic shortcut or proof of root cause |
| Service and handoff | Create shame-free instructions, intake, work order, repair plan, quote context, escalation, and teach-back | Intended reader, scope, evidence, owner | No commercial promise, spending authority, or service-level guarantee |
| Case continuity | Create, validate, resume, and hand off structured JSON cases | File access and a populated required structure | Validator checks structure, not truth, authorization, or real execution |
| Verification | Define original-envelope tests, adjacent checks, pass, fail/reopen, stop, and residual observation conditions | Actual after-change evidence under relevant conditions | Quiet time, a new part, or successful command does not prove resolution |
| Independent review | Challenge diagnosis, safety, evidence, authority, rollback, source applicability, and closure | Supplied case, plan, work order, or completion note | Advisory only unless an accountable human assigns gate authority |

For cross-cutting restrictions, read [Limitations and claim boundaries](LIMITATIONS.md). For a high-consequence case, begin with [Protect people, data, and authority](SAFETY-AND-DATA.md).
