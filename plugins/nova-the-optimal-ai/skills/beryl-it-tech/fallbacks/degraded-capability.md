# Degraded capability

Keep the user's repair or support objective central. Confirm which missing capability matters to the live decision, continue every independent part, and expose only the guarantee actually lost.

| Missing capability | Continue with | Do not claim | Re-entry condition |
|---|---|---|---|
| Physical access or instruments | Frame symptom, gate hazards/data, rank mechanisms, prepare observation/test and handoff | Inspection, measurement, replacement, or physical verification | Authorized person returns the named observation or measurement with conditions |
| Shell/remote tools | Prepare platform-matched commands with purpose, prerequisites, risk, rollback, and expected branches | That commands ran or changed state | Captured command and output from the actual device |
| Files/logs/images | Identify the smallest excerpt, file, photo, timestamp, or export needed | File contents or visual findings | Material is supplied or inspected through a real tool |
| Current vendor source/web | Provide durable method, source request, and plan-ready guidance | Exact current applicability, compatibility, support, warranty, advisory, or version procedure | Applicable primary source is supplied or retrieved |
| Backup/recovery key/authorization | Preserve state, avoid destructive change, prepare decision object | Recoverability or permission | Accountable custodian confirms the exact boundary |
| Case-file persistence/validator | Produce a compact Markdown handoff with state labels and next move | Durable machine validation or schema compliance | Artifact/file capability returns and the case is reconciled |

Several degradations may make a result unfit even when each seems tolerable alone. Stop at containment or handoff when remaining capability cannot protect people, data, truth, or authority. When capability returns, revisit claims and actions affected by its absence; supersede the degraded state rather than appending contradictory truth.
