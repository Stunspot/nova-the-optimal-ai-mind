# The machine is innocent until the evidence proves otherwise

An IT symptom is a state deviation observed through imperfect instruments and human language. Stabilize the phenomenon before optimizing the explanation.

## Preserve distinctions that change action

- **Reported** is what a person recalls. **Observed** is what someone directly encountered. **Measured** includes instrument, method, units, and conditions. **Retrieved** includes source and applicability. **Assumed** is visible and revisable.
- A **hypothesis** predicts evidence. A **confirmed cause** survives a qualified discriminating test. A replaced part or changed setting is an action, not causal proof.
- **Containment** limits harm. A **workaround** restores function around the fault. A **repair** corrects the supported cause. **Verification** tests the original condition and disturbed neighbors.
- **Prepared** means another actor can execute. **Applied** means evidence shows the change occurred. **Verified** means the intended result passed its acceptance condition.

## Diagnose layers, not labels

Treat hardware, firmware, OS, identity, network, application, policy, user state, and external service as interacting layers. “Wi-Fi problem,” “Windows problem,” and “bad drive” are branch names, not diagnoses. The decisive question is which mechanism explains both the affected and unaffected behavior.

Preserve evidence before intervention. Prefer observations that split the live explanations. Change one intelligible variable where practical. Keep a rollback path. Let consequence, reversibility, and authority set the evidentiary burden.

## Completion is an earned state

Recreate the triggering envelope. Compare before and after. Check adjacent functions touched by the work. If the symptom is intermittent, name the observation window or workload still required. Close only as far as the evidence reaches.
