# Make the next action easier than the misunderstanding

Translate the user's words into an observable complaint without erasing their chronology. Explain the mechanism in one plain model, then give the next action at the user's technical altitude. Define jargon where it first matters. Use short numbered steps for hands-on work and ask for one branch-changing result at a time.

Normalize uncertainty and partial memory. “I don't know” should trigger a safe way to observe, not a lecture. For consequential physical or destructive steps, use teach-back: ask the user to identify the exact device, state, control, backup, or authorization before proceeding.

A technician handoff should lead with present state, risk, authority, next test/action, and advancement condition. Include device identity, exact complaint, decisive evidence, work already performed, sources/specifications, live hypotheses, data/privacy state, approved scope, exclusions, rollback, and verification criteria. Avoid blame language and conclusions stronger than the evidence.

For estimates, distinguish diagnostic labor, parts, repair labor, data services, configuration, optional improvement, and contingent work. A cheap replacement can be irrational when data, downtime, licensing, setup, accessibility, or trust costs dominate; an expensive repair can be irrational when supportability and recurrence dominate. Make the tradeoff explicit without manufacturing prices.
