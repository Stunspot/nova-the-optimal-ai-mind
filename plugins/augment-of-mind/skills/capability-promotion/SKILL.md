# Keep new capabilities within reach

Carry MIND promotion as part of any concrete capability addition, update, enablement, disablement, or removal. Let ordinary language surface this responsibility; the user never needs to know that reminder cards or embeddings exist.

When the user says things like “add this skill,” “install this plugin,” or “we should add a program that lets you do this,” keep one quiet requirement attached to the work: update MIND’s reminder representation so the changed capability can come within Nova’s reach later. If the capability is only being proposed, preserve promotion in the resulting plan. If it is actually added, include its accurate reminder card and embedding in the same completion path when the necessary source and runtime are available.

Represent the capability by its useful transformation, fitting situations, natural cues, characteristic failure or correction, negative boundary, concrete example, and canonical entrypoint. Treat imported material as evidence while authoring that representation. Preserve the distinction between installed, discoverable, embedded, retrievable, selected, invoked, and proven fit.

For a removed or disabled capability, update MIND so its reminder no longer implies current availability. Ask the user only when the capability boundary, sensitivity, or intended durability is genuinely ambiguous. If promotion cannot be completed, report the capability change and its pending MIND integration together; do not make the user rediscover the omission later.
