# Capability Census v2

Status: replacement design; the live r6 snapshot remains active until a
qualified successor is built and atomically promoted.

## Why r6 must be superseded

The current database contains 1,185 source records, 1,182 distribution records,
546 capability identities, and zero lifecycle observations. Its sources include
809 GitHub `SKILL.md` copies, 268 plugin-cache copies, 59 repository README
derivations, and 41 then-installed skill copies. Individual capabilities carry
many unversioned copies: the Launch Operator has 15 distributions, Builder 11,
Pathfinder 11, and Omnicompetence 7.

The generation therefore confuses a useful transformation with places where
similar bytes happened to be found. It also promotes cloned third-party
repositories, cache backups, release fossils, and archived copies into Arm's
Reach while supplying no current installed, discovered, invoked, or healthy
evidence. Semantic qualification of that exact graph cannot repair a mistaken
ontology.

## The five ledgers

Never infer one ledger from another.

1. **Capability identity:** one durable useful transformation, promise,
   negative space, owner, aliases, and canonical entrypoint.
2. **Source custody:** the authority from which the capability definition is
   maintained, with digest, version, provenance, and custody state.
3. **Distribution:** a particular plugin, skill root, archive, program, or
   connector delivery of that capability.
4. **Lifecycle observation:** scoped evidence of custody, distribution,
   host presence, runtime use, fitness, or governance.
5. **Associative reminder:** the reviewed semantic representation that lets
   Nova recall the capability by transformation and situation.

A cached copy is a distribution or cache observation, never a new capability.
A README is documentation, not a capability, unless an explicit review admits
the program-level transformation it documents. Filesystem presence does not
mean installed; installed does not mean injected; injected does not mean
selected; selected does not mean invoked; invoked does not mean healthy.

## Admission classes

### A. Current host surfaces

Capture the exact task-level skill catalog, configured plugin inventory, and
exposed tools/connectors as time- and host-scoped observations. Do not persist
the surrounding prompt or task text. Catalog entries may reconcile to an
existing capability identity or create a review candidate; the catalog itself
does not establish canonical source or fitness.

### B. Owned canonical capabilities

Admit maintained Collaborative Dynamics skills, Augments, and private
production modules from an explicit allowlist of canonical repositories. A
capability may remain recallable when not installed if its useful
transformation is reviewed and the reminder clearly avoids implying present
availability.

### C. Programs and executable systems

Admit a program only when it offers a reusable transformation Nova may
materially need to remember and there is a stable invocation or handoff. Record
the executable/application as a distribution and current command/process/model
evidence as scoped lifecycle observations. Do not turn every executable on
`PATH`, every repository, or every local model file into a card.

### D. Candidates and outside praxis

Marketplace listings, cloned third-party repositories, skills.sh finds,
OpenClaw/Paperclip corpora, and recommended-but-uninstalled plugins remain in a
candidate ledger until Praxis Mine or accountable review accepts their
transformation. Candidate presence is not Arm's Reach promotion.

### E. Archives, releases, caches, and superseded material

Keep these in custody and disposition ledgers. They may prove recovery,
lineage, or version history, but do not receive independent active cards.
Superseded or retired capabilities retain explicit governance/custody state and
must not imply current availability.

## Initial successor scope

The first replacement generation should contain:

- the exact current host-exposed skill identities, reconciled across namespaces
  and duplicate distributions;
- the maintained Nova and MIND Faculties;
- the private Augment production capabilities Omnicompetence, Skill Pathfinder,
  Augment Mapper, Augment Skill Builder, Augment Launch Operator, Hesperos, and
  TestForge, whether or not the present host injects each one;
- a small reviewed set of locally important programs and systems, beginning
  with Codex, Git/GitHub custody, PowerShell, Python, Node, Ollama/local-model
  cognition, and any Liquid runtime actually observed;
- only relations that materially improve recall or sequencing.

The first successor explicitly excludes blanket GitHub-repository discovery,
README-derived repo capabilities, OpenClaw and Paperclip corpora, arbitrary
plugin-cache backups, archived ZIP members, and the entire marketplace catalog.

## Census workflow

1. **Declare sources.** Use an explicit, versioned allowlist. Each source has a
   purpose, authority, privacy class, scan kind, and expiry or review trigger.
2. **Collect candidates.** Run the bounded scanner only over declared roots or
   exact files. Preserve diagnostics and hashes; retain no source bodies in the
   report.
3. **Reconcile identity.** Group exact copies, version variants, renamed
   handles, product subskills, and genuinely distinct transformations. Select
   one canonical source per capability and record distributions separately.
4. **Review admission.** Mark each candidate `admit`, `candidate`, `duplicate`,
   `distribution-only`, `superseded`, `retired`, or `reject`, with rationale and
   reviewer.
5. **Author reminder cards.** For every admitted capability, record useful
   transformation, fitting situations, natural cues, characteristic failure,
   correction, negative boundary, concrete example, and canonical entrypoint.
   Every card carries exactly the six MIND semantic views.
6. **Record lifecycle evidence.** Create receipts for global custody,
   distribution, and governance states. Create expiring host/session receipts
   for installed, discovered, injected, selected, invoked, and fitness states.
7. **Compile deterministically.** The reviewed estate supplies timestamps,
   identities, cards, relations, profiles, and activation lineage. The compiler
   performs no discovery, model selection, semantic authorship, or hidden
   timestamp generation.
8. **Qualify before promotion.** Build in a disposable database; validate
   integrity, cardinality, source privacy, duplicates, boundaries, positive
   recall, near-neighbor discrimination, negative queries, and saturation.
9. **Promote atomically.** Back up the live database, set the r6 snapshot as the
   explicit predecessor, activate the complete successor transaction, reopen
   the database, and verify the durable activation receipt and current binding.
10. **Maintain incrementally.** Capability Promotion updates the identity,
    distribution, lifecycle, and reminder ledgers in the same completion path
    whenever a capability is proposed, added, changed, disabled, or retired.

## Required tooling changes

- Add a durable private reviewed-estate source; an active database snapshot is
  not adequate source custody.
- Add a versioned source allowlist and candidate disposition ledger.
- Extend the compiler or activation workflow to ingest global lifecycle
  observations and their receipts; the current builder emits empty lifecycle
  and mount arrays.
- Add duplicate-distribution and canonical-source validators.
- Add a saturation gate that fails when a normal task brings broad unrelated
  catalog families into Arm's Reach.
- Add a lifecycle rendering test so a remembered-but-unavailable capability is
  not presented as installed or healthy.
- Preserve predecessor snapshot IDs on every successor activation.

## Success criteria

The replacement is acceptable when:

- every active card corresponds to one reviewed transformation;
- every distribution points to one capability without multiplying identity;
- all canonical sources and agent-private records have explicit custody;
- current host states are receipt-bound, scoped, expiring, and non-inferred;
- no archive/cache/README-only object appears as an active capability;
- Omnicompetence is represented as Nova's private three-module Augment maker;
- Capability Promotion itself is present and recallable;
- representative semantic queries retrieve small useful neighborhoods without
  catalog floods;
- negative and boundary queries do not counterfeit availability or authority;
- the disposable database, backup, atomic activation, reopen, and rollback
  procedures are verified before r6 is superseded.
