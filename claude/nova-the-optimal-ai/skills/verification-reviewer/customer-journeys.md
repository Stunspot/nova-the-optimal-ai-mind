# Verify the customer outcome

For an interactive or information product, reconstruct the promise from the request, current contract and actual entry surface before accepting the submitted technical scope. A narrow code claim may be legitimate, but it cannot stand in for product readiness. State the omitted customer journey and reduce the verdict boundary when it was not exercised.

Start a cold walkthrough at the actual advertised entry point, in the intended runtime and with representative content. Use an outcome such as "find an accessible introduction to a topic I cannot yet name" rather than "click Explore, then this card." Record the visible cues and destination. An author-supplied deep link or explanation is assistance, not evidence of discovery.

For libraries, exercise known-item retrieval, subject browsing without a query, exploration of unfamiliar material, inspection of a preview, source reading, and return to the same position/filters. Check meaningful subject labels, collection purpose, collection versus course versus saved-list semantics, accurate counts, source provenance, and reasons for related items. Random selection alone does not establish useful serendipity.

For learning tools, ask what the learner will be able to do, what they need beforehand, where to begin, where they are now, what follows and why, how to practice, and what their progress means. Distinguish opened, practiced, self-reported understanding and demonstrated performance. Test saved work across refresh, return, route changes and failure recovery; do not promote a click to mastery.

For shared navigation and themes, follow entry → overview → detail → adjacent task → return → resume. Exercise every supported theme on real controls, reading panels, menus, focus, selected, disabled and error states at representative narrow/wide sizes. Root token values, a screenshot of one page or absence of JavaScript errors is insufficient: inspect rendered text/background combinations and operate the path.

Treat content shape as test data: realistic record counts, long titles, missing metadata, empty subsets, duplicate works, stale links and delayed saves. A ten-record synthetic catalog cannot establish the usability of a five-hundred-record library. Use a faithful bounded sample when the real corpus cannot be accessed and name the scale boundary.

Record each material journey as actor/context; start; uncoached task; expected visible comprehension and persistent result; forbidden loss; observed steps; evidence; unresolved boundary. Practitioner/browser walkthroughs establish observed operation and expert diagnosis. They do not fabricate participant performance or accessibility conformance. A missing navigation edge is a product finding; a missing user study is an evidence limit, not automatically a release blocker.

## Challenge a pending operation against current user work

For a task that loads, replaces, saves or applies work after the next user action, ask where its permission and target remain valid at commit. Inspect a trace that pauses an actual asynchronous boundary, changes or cancels the relevant draft/record, releases the pending result, and observes both visible and persisted effects. The operator should identify the target, draft revision and request generation at the start and at mutation. A check performed only before the wait can protect yesterday's state while destroying today's work.

Challenge the claimed interaction contract at its real boundary. If serialized, did the actual conflicting edit/navigation remain unavailable, with a visible pending state until all asynchronous work ended, and did success/cancel/failure restore it? If editable, what preserves a newer draft or obtains current permission, including across an asynchronous confirmation? Does cancelled or superseded work stay invalid after its delayed callback resolves? Can an old editor apply to a newly selected record? A blocked handler, an import button or an abort call alone establishes none of those outcomes.

For a read that overlaps a write, can an older snapshot roll back the visible catalog after a successful save? Compare the rendered result with authoritative saved state and the claimed freshness; preserved storage alone cannot excuse a falsely current display.

Read the preserved original and successor states, not merely the final title or success message. Demand a matched useful control: the intended replacement commits exactly once and a same-file retry succeeds after cancellation or failure. An all-reject implementation is not safe completion. A deterministic reducer trace establishes state logic; actual browser input is needed to claim visible inert/busy behavior and event wiring. A fixture demonstration establishes its oracle, not this candidate's behavior or model adherence.

A consequential loss or wrong-record write is a product defect and ends that frozen candidate's cycle. Missing decision-critical interleaving evidence limits the affected readiness claim; it does not invent a defect. Keep this lens conditional on the candidate's exposed operation and preserve supported narrower claims.

## Distinguish an observed outcome from a broken probe

Challenge the browser apparatus at the claimed boundary. Were controls selected from the observed interface, uniquely scoped and in the asserted disclosure state? Preserve a locator or syntax failure as apparatus evidence until the actual user affordance distinguishes a product defect. An expected control absent from the real interface can still be a product finding; a guessed name alone cannot establish it.

When a run stops after useful work, inspect the exact completed observations and their post-state artifacts against this candidate. Keep the command failed or interrupted, attribute supplied observations, and leave the unexecuted tail visible. Accept a bounded observation only if its oracle was reached and the later failure cannot invalidate it. A real saved-file edit may remain supported while an untouched return or disclosure check remains missing. Required guarantees still govern readiness, and the single-support-recovery limit still governs attempts; neither the report nor a partial trace creates an exception.
